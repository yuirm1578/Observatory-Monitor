# Observatory Monitor — 가상 천문 관측 장비 모니터링·제어 클라이언트

망원경·돔·CCD 카메라·기상 센서로 구성된 가상 관측 장비를 TCP로 모니터링하고 제어하는 WPF 클라이언트, 그리고 그 장비를 대신하는 시뮬레이터.

> **상태:** 구현 착수 전 — ICD([`PROTOCOL.md`](PROTOCOL.md) v0.2)를 먼저 확정했고, 구현은 아래 [진행 현황](#진행-현황)의 마일스톤 순서로 진행합니다.

## 왜 만들었나

장비 제어 SW는 실장비로 개발하기 어렵습니다. 장비는 비싸고, 라인에 물려 있고, 고장을 일부러 낼 수도 없습니다. 그래서 통신 규격 문서(ICD)를 먼저 정하고, 그 문서만 보고 **장비 대역(시뮬레이터)** 과 **클라이언트**를 각각 구현합니다.

이 프로젝트는 그 개발 방식을 그대로 따라가면서, 실장비로는 만들 수 없는 조건(무응답, 온도 상승, 강풍)을 시뮬레이터로 마음대로 재현해 클라이언트의 오류 처리를 검증하는 것이 목표입니다.

## 구성

```
PROTOCOL.md                ← ICD: 통신 규격 (먼저 작성, 유일한 기준)
Telescope.Simulator/       ← 콘솔, TCP 서버 — 장비 대역 + 결함 주입 도구
Observatory.Monitor.Core/  ← 파서, 명령 클라이언트(Timeout·Retry), 알람 엔진, 로그·리플레이 (UI 의존 없음)
Observatory.Monitor.Wpf/   ← WPF/MVVM 클라이언트 (View·ViewModel만)
Observatory.Tests/         ← 단위·통합 테스트 (xUnit)
```

```
[Telescope.Simulator.exe]  ←── TCP 5000, 한 줄 = 한 메시지 ──→  [Observatory.Monitor.exe]
```

## 기능 5개

### 1. 연결 / 상태 표시
TCP 연결 상태와 장비 상태(`IDLE` · `SLEWING` · `TRACKING` · `FAULT`), 돔 상태, 현재 고도·방위각을 실시간으로 표시합니다. 연결이 끊기면 자동 재접속합니다.

### 2. 실시간 차트
CCD 온도, 습도, 풍속을 [LiveCharts2](https://livecharts.dev/)로 실시간 그립니다. 온도 차트에는 이동평균과 ±3σ 관리 한계선을 함께 표시합니다.

### 3. 알람
- 임계치 알람: 값이 WARN/CRIT 한계를 넘으면 화면에 표시하고 이력에 기록합니다.
- 통계 알람: 직전 60개 샘플의 이동평균 + 표준편차 기반 3σ 이상 감지 — 스파이크·급변 검출용 (통계적 공정 관리, SPC 개념). 완만한 상승은 임계치 알람이 맡습니다.
- 알람 이력은 발생·해제 시각과 함께 보관합니다.

### 4. 명령 전송 → 응답 대기 → Timeout · Retry · Recovery
`SLEW`, `TRACK`, `ABORT`, `OPEN_DOME`, `CLOSE_DOME`, `RESET` 명령을 보내고 `ACK`를 기다립니다. 응답이 없으면 같은 명령 ID로 재전송하고, 서버는 중복 ID(접속 단위 캐시)를 재실행하지 않고 저장된 응답을 돌려줍니다. 재시도가 모두 실패하면 실제 장비 상태를 확인하고 재접속합니다.

### 5. 로그 파일 기록 + 리플레이
송수신한 프로토콜 원문을 타임스탬프와 함께 파일에 기록하고, 저장된 로그를 라이브와 **같은 파서**로 다시 재생합니다 (×1 / ×5 / ×10).

### 안전 인터록
습도 또는 풍속이 한계를 넘으면 시뮬레이터(장비 측)가 상태와 무관하게 스스로 이동·추적을 중단하고 돔을 닫습니다. 클라이언트가 죽어도 장비는 안전 상태로 갑니다. 해제는 조건 회복 후 사람이 `RESET`을 보내야만 가능합니다. 클라이언트는 이를 상태와 알람으로 표시합니다.

## 시뮬레이터

장비인 척하는 콘솔 프로그램이자 테스트 도구입니다.

- 포트 5000에서 접속을 기다리고, 1초마다 `DATA` 한 줄을 보냅니다.
- `CMD,SLEW` 수신 시 `ACK`를 보내고 상태를 `SLEWING`으로 바꿉니다.
- **3% 확률로 명령에 응답하지 않습니다** (명령은 실행하고 ACK만 안 보내는 경우 / 수신 자체를 버리는 경우) → Timeout · Retry · 중복 처리 검증
- **CCD 온도를 서서히 올립니다** → 임계치 알람 검증
- **`spike` 명령으로 급변 값을 주입합니다** → 3σ 통계 알람 검증

```
> Telescope.Simulator --port 5000 --drop-rate 0.03 --drop-mode both --ccd-drift 0.02 --scenario normal --seed 42
```

런타임 콘솔 명령(`drop`, `hang`, `storm`, `fault`, `spike`)으로 완전 무응답·링크 단절·강풍·CCD 이상·급변 값을 즉시 재현할 수 있습니다. 자세한 내용은 [PROTOCOL.md 11장](PROTOCOL.md).

## 프로토콜 한눈에 보기

```
S→C  DATA,TEMP=-19.8,HUM=62,WIND=3.2,ALT=45.0,AZ=180.0,STATE=TRACKING,DOME=OPEN,ILK=0
C→S  CMD,SLEW,ID=17,ALT=60,AZ=200
S→C  ACK,SLEW,OK,ID=17
S→C  EVT,SLEW,DONE,ALT=60.0,AZ=200.0
```

전체 규격(메시지 형식, 상태 전이, 인터록, 알람, 로그 형식)은 [`PROTOCOL.md`](PROTOCOL.md)를 참고하세요. 개념·명명은 ASCOM 인터페이스를 참고했으며, 대응표는 PROTOCOL.md 12장에 있습니다. (이 프로젝트의 전송 방식은 Alpaca REST가 아니라 TCP 라인 프로토콜입니다.)

## 테스트 (예정)

- **단위:** PROTOCOL.md의 예제 줄을 양쪽 파서에 같은 문자열로 넣는 골든 샘플 테스트, 상태 전이 표 한 줄 = 테스트 한 케이스, 알람 히스테리시스·3σ 경계 케이스
- **통합** (시뮬레이터를 같은 프로세스에서 임의 포트로 띄움):
  1. `drop 1.0` → 3회 시도 후 `FAILED(TIMEOUT)`
  2. ACK만 유실(`--drop-mode ack`) → 명령이 중복 실행되지 않음
  3. `hang` → 링크 단절 감지, 재접속, 상태 동기화
  4. `storm` → 인터록 발동, `RESET` 전까지 `ERR=INTERLOCK`

## 설계 메모

- **ICD 먼저:** 시뮬레이터와 클라이언트는 서로의 코드를 보지 않고 `PROTOCOL.md`만 보고 구현합니다. 규격이 바뀌면 문서를 먼저 고칩니다.
- **인터록은 장비 측:** 안전 정지는 클라이언트 연결과 무관하게 동작해야 하므로 서버에 둡니다.
- **재시도는 멱등하게:** 무응답이 "명령 미수신"인지 "ACK만 유실"인지 클라이언트는 알 수 없으므로, 명령 ID로 중복 실행을 막습니다.
- **로그는 원문 그대로:** 파싱 결과가 아니라 송수신한 줄을 저장해서, 리플레이가 실제 수신 경로를 그대로 검증합니다.
- **코드는 공유하지 않기:** 시뮬레이터와 클라이언트는 파서를 각자 구현하고, 규격 적합성은 ICD 예제 줄을 양쪽 테스트에 똑같이 넣어 확인합니다.
- **시간은 주입하기:** Timeout·하트비트·3σ 창·리플레이가 같은 시계 추상화(`TimeProvider`)를 쓰므로, 테스트에서 시간을 조작해 재현할 수 있고 리플레이는 로그의 시각으로 동작합니다.
- **알람 역할 분담:** 완만한 상승은 임계치 알람, 급변은 3σ 통계 알람이 맡습니다 (PROTOCOL.md 9장).
